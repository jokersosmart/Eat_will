## 1. 產品摘要

「阿是要不要好好吃飯」是一個以**商務飯局策略**為核心的 Web 應用。它協助亞洲地區需要認識人、爭取資源、建立品牌或擴大影響力的使用者，在飯局前形成可執行策略、於互動中辨識角色與調整話題，並在局後保存紀錄及反思下一步。

本產品不以泛用聊天或社交建議取代使用者判斷。所有策略輸出必須以既有課程知識庫、五局十五層、七大角色及已審核研究補充為根據；資料不足時，系統應明確說明限制，而非補造對象意圖、談判條件或文化偏好。[1] [2]

> **產品承諾：** 在每一張餐桌上，協助使用者把「不知道該聊什麼、該注意誰、下一步該怎麼做」轉為可追溯、可執行、可復盤的飯局決策。

## 2. 問題定義與目標

商務飯局通常同時包含關係建立、資訊蒐集、資源協作與聲譽管理；使用者容易因為準備不足、錯估互動深度，或急於推進而失去節奏。產品的核心目標是降低局前的認知負擔，讓使用者能以少量條件建立策略草圖，並透過釐清提問補足真正影響決策的資訊缺口。

| 目標 | 可觀察的產品結果 | MVP 狀態 |
| --- | --- | --- |
| 局前準備 | 可按人數、菜系、時段、局別與層次取得相符策略 | 已完成 |
| 角色判讀 | 可查看七大角色的訊號、策略及注意點 | 已完成 |
| 對話推進 | 可依五局十五層取得話題方向與注意事項 | 已完成 |
| 不完整資訊下的規劃 | 可先產生假設、釐清問題、注意事項與下一步 | 已完成 |
| 個人化與復盤 | 登入後可保存飯局紀錄與常用情境預設 | 已完成 |
| 來源可追溯性 | 研究補充可顯示來源、連結與適用邊界 | 已完成 |

本期**不納入**餐廳訂位、支付、即時錄音、第三方社群資料抓取、未經同意的與會者分析，或以模型推論個人權力關係與文化身份的功能。

## 3. 目標使用者與核心工作

| 使用者群組 | 典型情境 | 需要完成的工作 | 系統提供的支援 |
| --- | --- | --- | --- |
| 商務開發者與創業者 | 希望與潛在客戶、合作夥伴或投資人建立下一步 | 在有限時間內建立信任並確認合作方向 | 局前規劃、情境引導、推進與成交階段建議 |
| 品牌／社群經營者 | 需要經營介紹人、媒體、意見領袖或社群節點 | 在不過度推銷下辨識橋接與資源機會 | 七大角色、探索階段問題、關係階段追蹤 |
| 職場專業者 | 跨部門、客戶或前輩飯局前感到不確定 | 判斷對話深度與安全的下一步 | 新手引導、五局十五層、注意事項 |
| 飯局主持人 | 安排多方參與者並維持互動品質 | 讓不同角色被看見且對話不失控 | 人數／菜系／時段篩選、角色卡與話題結構 |

## 4. 產品範圍與固定知識規則

### 4.1 不可任意改名的核心架構

| 架構 | 固定內容 | 產品用途 |
| --- | --- | --- |
| 六大部分 | 目標與框架、人物與角色、場景、時機、話題與五局、實戰與長期養成 | 知識庫分類與局前推薦來源 |
| 七大角色 | 資源人、需求人、橋接人、主持人、氣氛人、觀察人、干擾人 | 角色辨識與應對策略 |

| 公開前台規則 | Q&A 分類保留於底層，但不顯示於前台、局前推薦或智慧建議 | 避免問題解答內容干擾策略閱讀 |

上述名稱是產品知識結構與前台篩選邏輯的一部分。若要改名或新增角色／局別，須同時更新資料模型、篩選規則、前端文案、測試與既有內容，不能只修改畫面文字。[1] [3]

## 5. 主要使用者旅程

使用者開啟首頁後，先從「局前規劃」選擇人數、菜系與時段；新手可以直接套用模擬範例。若目標或人物背景尚未清楚，使用者先按下「先釐清這一局」，讓系統把目前已知條件與尚未確認的條件分開呈現。使用者可將釐清問題一鍵帶回目標或人物背景欄位，補齊資訊後再產生正式智慧建議。

正式建議必須引用相符的課程條目，並可補充至多三筆研究條目。使用者可再切換到角色識別、五局十五層或知識庫閱讀依據。登入後，使用者可把本次規劃與局後筆記存入個人飯局紀錄，為後續關係追蹤留下脈絡。[1] [2]

| 旅程階段 | 使用者問題 | 預期系統反應 | 成功訊號 |
| --- | --- | --- | --- |
| 局前 3 分鐘 | 「我該從哪裡準備？」 | 提供 30 秒選擇指南與情境欄位 | 使用者完成基本條件選擇 |
| 資訊不足 | 「我還不知道真正要談什麼。」 | 提出可修正假設與不超過四個釐清問題 | 使用者補充目標或人物背景 |
| 策略形成 | 「這一局該怎麼推進？」 | 顯示對應策略、角色訊號與話題深度 | 使用者可說出下一步行動 |
| 飯局結束 | 「下次要怎麼接續？」 | 產生局後復盤與可保存的紀錄 | 使用者保存筆記與後續行動 |

## 6. 功能需求與驗收準則

| 編號 | 需求 | 驗收準則 |
| --- | --- | --- |
| FR-01 | 局前規劃須依人數、菜系、時段篩選策略條目 | 篩選結果僅包含標籤相符且可公開的條目 |
| FR-02 | 系統須顯示指定七大角色與五局十五層 | 前台不出現未定義角色或非固定局別 |
| FR-03 | 智慧建議與情境引導須受知識庫約束 | 每次回覆帶有依據條目；來源不足時不臆測 |
| FR-04 | 情境引導須區分事實、假設與待確認資訊 | 假設最多三項、問題最多四題、注意事項最多四項 |
| FR-05 | 研究補充須保留來源名稱、網址及使用邊界 | 研究條目可在知識庫與智慧建議中被追溯 |
| FR-06 | 個人飯局紀錄與預設僅允許本人讀寫 | 以受保護程序和使用者 ID 作資料隔離 |
| FR-07 | 行動裝置與桌面版須保持表單與來源連結可讀 | 長來源名稱可換行；互動按鈕可點擊 |
| FR-08 | Q&A 分類不可進入公開知識庫或模型來源組合 | 公開查詢、局前推薦與智慧建議均排除 Q&A |

## 7. 資料與技術設計

產品以 React 前端、Express／tRPC 後端及 MySQL/TiDB 資料庫組成。前端應透過 tRPC 呼叫功能模組；不可另建未經管理的 REST 包裝。登入由 Manus OAuth 管理，個人資料寫入僅能經受保護程序進行。[3] [4]

| 資料實體 | 目的 | 主要可調整欄位 |
| --- | --- | --- |
| `knowledge_entries` | 六大部分課程與研究補充 | section、category、title、content、三種篩選標籤、來源與適用邊界 |
| `dinner_roles` | 七大角色內容 | definition、signals、strategy、notes |
| `conversation_stages` | 五局十五層內容 | coreFocus、topicGuidance、cautions |
| `dinner_records` | 個人規劃與復盤 | 目標、情境、建議、反思與時間戳記 |
| `user_preferences` | 個人常用局前條件 | defaultGuestCount、defaultCuisine、defaultTimeSlot |

## 8. 如果要應用或改造，可以改哪裡

下表將「可調整」與「需審慎調整」分開。產品內容通常可在資料或設定層完成；改變知識架構、資料表或模型規則則需要完整工程流程。

| 想調整的項目 | 優先修改位置 | 是否需要資料庫遷移 | 注意事項 |
| --- | --- | --- | --- |
| 新增／修改研究補充內容 | `server/data/auxiliaryKnowledge.ts` | 否；既有欄位足夠時 | 必填來源名稱、URL 與使用邊界；不可寫成未驗證事實。[5] |
| 新增課程策略條目 | `knowledge_entries` 的匯入資料與資料庫 | 視欄位而定 | 設定 section、category、三種標籤及排序；確認不屬於 Q&A 公開排除類別。 |
| 調整七大角色的文案 | `dinner_roles` 資料 | 否 | 可以修訂定義、訊號與策略；不要任意改角色名稱。 |
| 調整五局十五層話題 | `conversation_stages` 資料 | 否 | 可以優化做法與注意事項；保持五局及每局三層結構。 |
| 增加使用者預設 | `drizzle/schema.ts`、`server/db.ts`、`server/routers/dinner.ts`、局前表單 | 是 | 例如產業、職位、常見對象；須新增 migration、讀寫程序與測試。 |
| 調整情境引導問題邏輯 | `server/routers/advice.ts`、`docs/SCENARIO_GUIDANCE_SPEC.md` | 否 | 維持「事實／假設／問題」分界與固定備援。 |
| 調整智慧建議提示與輸出 | `server/routers/advice.ts` | 否 | 不可移除來源約束、Q&A 排除、逾時備援與結構化解析。 |
| 調整首頁文案或視覺 | `client/src/pages/Home.tsx`、`client/src/index.css` | 否 | 保持暖米白、金色、深海軍藍的可讀性與響應式設計。 |
| 新增個人化模組 | schema、db、對應 router、前端頁面與測試 | 通常需要 | 先寫需求與資料模型，再生成 migration 並套用。 |

### 8.1 內容維護標準

課程條目應忠於原始課程材料；研究補充則需有可公開存取的來源連結、來源名稱和適用範圍。對於跨文化互動、合規或權力關係，內容應提醒使用者確認情境，不得把群體特徵或未確認身份當成個人事實。研究來源的完整紀錄應保留在 `docs/AUXILIARY_KNOWLEDGE_RESEARCH.md`。[5]

### 8.2 工程變更流程

任何功能調整應遵循「**先規格、再資料、後 API 與介面**」的順序。涉及表格欄位時，先更新 `drizzle/schema.ts`，使用 Drizzle 生成並審核 migration，再套用資料庫變更；接著更新 `server/db.ts` 與對應 tRPC router，最後讓前端使用 `trpc.*` hooks 串接，並補上 Vitest 測試。[3] [4]

## 9. LLM 與資料治理規則

智慧建議和情境引導都只能在伺服器端呼叫模型。每次呼叫會帶入情境相符的公開課程條目、角色內容及對話層次；課程條目優先，研究補充最多三筆。模型回覆以結構化 JSON 驗證；若逾時或解析失敗，系統應回傳固定的知識庫備援，而非轉為開放式回答。[1] [2]

| 規則 | 必須行為 | 禁止行為 |
| --- | --- | --- |
| 來源約束 | 顯示依據條目；研究補充保留可追溯來源 | 無來源地推論他人意圖或商務條件 |
| 不確定性 | 使用「若」「尚未確認」標示假設 | 把假設寫成既定事實 |
| 個人資料 | 只保存使用者主動輸入的飯局內容 | 抓取、推論或外洩未授權的與會者資料 |
| 合規與文化 | 提醒確認公司政策、招待邊界與個別偏好 | 把文化標籤當成自動適用規則 |

## 10. 發布、測試與維護

本機開發前需設定資料庫、OAuth 和內建服務環境變數；敏感環境變數不得提交到 Git。主要驗證指令如下。

```bash
pnpm install
pnpm check
pnpm test
pnpm build
pnpm dev
```

| 變更類型 | 最低驗證要求 | 建議補充 |
| --- | --- | --- |
| 知識內容調整 | 篩選與公開排除規則測試 | 檢查來源及使用邊界是否完整 |
| 路由／模型變更 | 型別檢查、單元測試、備援案例 | 加入輸入無效與來源不足案例 |
| 表單與互動變更 | 前端互動測試 | 桌面及 375px 手機畫面驗證 |
| 資料表調整 | migration 審核與資料庫驗證 | 確認既有使用者資料不受影響 |

每個可交付版本都應建立專案快照；程式、規格、測試與文件同步至公開 GitHub repository，讓後續可在 VS Code 進行規格驅動開發。
